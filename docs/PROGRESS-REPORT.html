1定案：TGS = 终端图形 API

从第一性原理推导：TGS = 程序 ⇄ 渲染器的点对点绘制协议。一程序一画布。 协议只回答两个问题：画什么（绘制原语）和输入怎么来（事件）。 像图形 API（X11/OpenGL/Wayland）一样——不提供控件、不提供布局、不提供焦点。 那三层是 toolkit 的，在程序侧组合。

决策内容状态
协议 = 绘制语义 线上只有 3 个绘制原语 + 事件；无控件目录、无 win_id、无焦点 定案
无窗口管理 合成器不管理窗口/激活/z-order——那是外层 WM 的事；协议无 win_id 定案
无焦点模型 焦点是图形 API 层概念（窗口级键盘路由），不由终端实现；控件级焦点完全程序侧 定案
IME 独立程序 IME 是独立程序，候选词由 IME 程序自己绘制（外层 WM 呈现）；TGS 只做输入变换管道 定案
TGS ⊃ kitty 帧走 kitty G APC 通道；呈现层用 kitty 图形序列；超集=能力包含+扩展 方案待裁决
第一性判据：协议只承载机制（server holds mechanism）—— 绘制、命中、输入采集、IME 管道。一切策略（布局、控件、焦点、文本缓冲、值状态） 在程序侧（program holds policy）。

4帧格式：kitty G APC 通道

TGS 帧走 kitty 图形协议的 APC 通道：ESC _ Gtgs;<payload> ESC \。 Gtgs; 标记 TGS 超集帧；kitty 原生帧是 ESC _ G<key=value,...>;<data> ESC \。 两者共享同一 APC 通道——解析器双识别。

待裁决：kitty 协议通过"未知 key 静默忽略"提供隐式扩展兼容， 但没有正式扩展声明。当前 Gtgs; 格式不是合法 kitty key=value 语法。 两个修正方案：
A) 改为合法 kitty 格式 Gtgs=1,c=create,...;（kitty 终端忽略 tgs=1）
B) 用独立前缀 TGS;（与 kitty G 帧共存，不扩展 kitty 帧）
超集=合成器同时理解两种帧，不依赖 kitty 的扩展能力。

6合成器与客户端

合成器（window_manager.c）

薄路由：帧→后端元素调用，输入事件→程序（或 IME 管道）。无焦点、无订阅门控、无几何回报、无布局。

客户端（tgs_client）

元素 API：create_element / update_element / set_element_style / destroy_element + poll_event。 程序自持一切状态——文本缓冲、值、焦点、布局。
